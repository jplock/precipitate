= 0001 working notes: facts and sources

Collected facts for writing RFD 0001. Not part of the design document.
Verify anything marked (unverified) before relying on it.

== Oxide hardware and limits

* Rack: up to 32 Gen 1 sleds or up to 24 Gen 2 sleds.
  Source: https://oxide.computer/product/specifications
* Gen 1 sled: AMD EPYC 7713P (64 cores), 512 GiB or 1 TiB DRAM.
* Gen 2 sled: one AMD EPYC 9005 (up to 192 cores), 768 GiB, 1152 GiB or
  1.5 TiB DDR5, ten NVMe bays, 2 x 100 GbE.
* Per rack, guest resources: up to 7,875 vCPU, 30.6 TiB memory, 1.7 PiB NVMe
  block storage.
* Guest memory reservoir: 91% of DRAM after subtracting page tables
  (`physical / 4096 * 120` bytes) and a 44 GiB control plane earmark, since
  release 21 (86.3% before). Works out to about 85% of physical DRAM.
  Source: https://docs.oxide.computer/release-notes/system/21,
  https://github.com/oxidecomputer/omicron/pull/10791
* Per-instance vCPU cap: 64 in older release notes vs. 254 in the current
  console. Release-dependent.
  Source: https://docs.oxide.computer/release-notes/system
* Per-instance memory: up to 1.5 TiB on sleds with 2 TiB DRAM.
* Disks per instance: 12 in current docs vs. 8 in RFD 595.
* Max disk size 1023 GiB; disks are thick-provisioned.
* Disks cannot be resized after creation: no resize endpoint in
  `nexus-latest.json` (2026091500.0.0); also RFD 595.
* Disk attach and detach require the instance to be stopped (RFD 595).
* Disk types: `distributed` (Crucible) and `local` (blank only).
  Source: `DiskBackend` schema in Omicron `openapi/nexus/nexus-latest.json`
* Crucible keeps three copies on separate sleds (secondary source: Series D
  press coverage; treat as a parameter).

== Images and migration path

* Oxide imports RAW images only; convert with
  `qemu-img convert -f vmdk|qcow2 -O raw`.
* Guests need UEFI boot, cloud-init with a NoCloud config drive, virtio
  drivers.
* `oxide disk import` uploads in chunks via bulk-write endpoints; URL import
  was removed in release 5.
  Sources: https://docs.oxide.computer/guides/creating-and-sharing-images,
  https://docs.oxide.computer/cli/disk/import
* No Oxide-published migration tooling or guide was found.

== Capacity principles (RFD 70)

* "Do not over-provision or allow for over-provisioning."
* Terms: in-use, provisioned, reserved, capacity, utilization, threshold.
* Always tell the user which utilization formula was used.
* Default threshold: 75% of capacity.
* Show remaining capacity as "how many instances of what size remain".
* Source: https://rfd.shared.oxide.computer/rfd/0070 (state: discussion)

== Units (RFD 203)

* Memory and storage: bytes with base-2 prefixes (KiB, MiB, GiB, TiB, PiB).
* Network throughput: bits per second with base-10 prefixes (Kbit/s).
* Vendor base-10 capacity: show both, e.g. "3.2 TB (2.9 TiB)".
* Source: https://rfd.shared.oxide.computer/rfd/0203

== Networking (RFD 21 and current docs)

* Firewall rules are stateful; priority 0-65535, lowest evaluated first;
  deny wins ties at equal priority; allow and deny actions.
* Targets and filters: `vpc`, `subnet`, `instance`, `ip`, `ip_net`
  (`VpcFirewallRuleTarget` in `nexus-latest.json`). No tags; no equivalent of
  one security group referencing another.
* New VPCs get default inbound rules: SSH (TCP 22), ICMP, and intra-VPC
  traffic. Implicit rules: allow all outbound, deny all inbound.
* Rule updates go through `vpc_firewall_rules_update` (whole set).
* Sources: https://rfd.shared.oxide.computer/rfd/0021,
  https://docs.oxide.computer/guides/configuring-guest-networking
* AWS contrast: security groups are allow-only, stateful, attached per ENI,
  unioned across groups; NACLs are stateless with deny.

== Tenancy (RFD 297)

* Siloed resources (projects, instances, disks) are fully isolated per silo.
* Non-siloed resources (racks, sleds, global images) look the same in every
  silo.
* Source: https://rfd.shared.oxide.computer/rfd/0297

* AWS Migration Evaluator, Azure Migrate, RVTools-driven sizing: ingest

== Resolved open items

Checked against Omicron `main` as of 2026-10-12. These are the values in the
code; confirm against the release a customer actually runs.

=== Instance limits (Omicron source)

* Max disks per instance: *12* (`MAX_DISKS_PER_INSTANCE` in
  `nexus/db-queries/src/db/queries/disk.rs`). RFD 595's figure of 8 is out
  of date.
* Max vCPU per instance: *254* (`MAX_VCPU_PER_INSTANCE`,
  `nexus/src/app/mod.rs`). The 64 in older release notes is out of date.
* Memory per instance: *1 GiB to 1.5 TiB*. The source comment says the cap
  keeps sizes "in ranges that we've tested", not to prevent overallocation.
* Disk size: *1 GiB to 1023 GiB*.
* Max NICs per instance: *8* (`nexus/db-model/src/network_interface.rs`).
* Max external IPs per instance: *32*, of which at most 2 ephemeral.

=== Changes that require a stopped instance (Omicron source)

* Changing CPU or memory: "instance must be stopped to change CPU or memory"
  (`nexus/db-queries/src/db/datastore/instance.rs`).
* Setting the boot disk: "instance must be stopped to set boot disk".
* Attaching disks: allowed only in `Creating` or `NoVmm` (stopped) states;
  source comment: "We currently only permit attaching disks to stopped
  instances" (`nexus/db-queries/src/db/datastore/disk.rs`).
* Attaching or updating network interfaces: instance must be stopped
  (`nexus/db-queries/src/db/queries/network_interface.rs`,
  `datastore/network_interface.rs`).

=== EC2 VM export constraints (AWS VM Import/Export)

Source: https://docs.aws.amazon.com/vm-import/latest/userguide/limits-image-export.html

* Output formats: VHD, stream-optimized VMDK, or raw. Raw avoids a
  `qemu-img` conversion step for Oxide.
* Destination: an S3 bucket in the same account; SSE-KMS encrypted buckets
  are not supported.
* Cannot export:
** images containing AWS-provided third-party software (e.g. Windows, SQL
   Server) or created from an AWS Marketplace image;
** images with encrypted EBS snapshots in the block device mapping;
** AMIs shared from another account.
* The instance's base AMI must still exist.
* Only EBS volumes in the launch-time block device mapping are exported;
  volumes attached after launch are not.
* Volumes larger than 1 TiB are not supported (Oxide's per-disk max is
  1023 GiB, so the two limits nearly coincide).
* Boot: GRUB2 enabled for BIOS or UEFI, not both.
* One export task per AMI at a time; 5 concurrent conversion tasks per
  region by default (raisable to 20).

Implication for precip: Windows instances, Marketplace-derived instances and
anything on encrypted EBS (common, often by default) cannot use VM export.
Those need another path (rebuild from source images, or block-level copy
from a snapshot into a raw image), and the report should flag them
separately.

== Operator guide: resource management

Source: https://docs.oxide.computer/guides/operator/resource-management
(and https://docs.latest.oxide.computer/guides/operator/resource-management),
accessed 2026-10-13.

* Maximum usable capacity per sled: 853 GiB memory (current docs) vs
  809 GiB (latest docs); 27,298 GiB (26.6 TiB) storage in both.
* Full rack (24 sleds): 26.6 TiB vs 25.2 TiB memory; 853.0 TiB storage.
* Per instance: up to 254 vCPUs, up to 12 attached disks.
* Guidance: keep the sum of silo quotas at or below usable rack capacity;
  maintain a 15-30% buffer of compute for placement flexibility (random
  sled selection), dynamic workloads, maintenance windows, and instance
  migrations.
* Utilization formulas per silo: provisioned ncpus / vcpu quota, provisioned
  memory / memory quota, disks + snapshots size / storage quota.
* "The maximum usable capacity may be adjusted in future versions."
